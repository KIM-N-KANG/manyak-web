# 릴리스 진행 (manyak-web)

## 목적

`dev`에 머지된 변경을 `release/v{버전}` 브랜치로 묶어 `main`에 반영하고, 버전 태그로 GHCR 릴리스 이미지를 발행합니다. 핵심은 이전 릴리스와 동일한 패턴(PR 2건, 머지 커밋, lightweight 태그)을 유지하고, 머지·태그처럼 되돌리기 어려운 단계 전에 사용자 확인을 받는 것입니다.

## 팀 규칙

- 브랜치: `release/v{버전}` (예: `release/v0.2.8`), `origin/dev`에서 분기합니다.
- 버전: `package.json`의 `version` 한 줄만 변경합니다. 커밋 메시지는 `[KNK-{티켓}] Chore: 패키지 버전 v{버전}로 변경`.
- PR은 항상 2건 한 쌍입니다.
  - 릴리스 PR: `release/v{버전}` → `main`, 제목 `[KNK-{티켓}] Release: v{버전}`
  - dev 동기화 PR: `release/v{버전}` → `dev`, 제목 `[KNK-{티켓}] Chore: v{버전} 버전 dev 동기화`
- 둘 다 Draft로 만들고, CI 통과 후 Ready 전환 → **머지 커밋**(`--merge`)으로 머지합니다. squash·rebase를 쓰지 않습니다 — 두 PR이 같은 버전 커밋을 공유하므로 머지 커밋이어야 dev와 main의 히스토리가 어긋나지 않습니다.
- 태그: main 머지 커밋에 **lightweight** 태그 `v{버전}`을 붙여 푸시합니다. annotated 태그를 쓰지 않습니다(기존 태그 전부 lightweight).
- 태그 푸시가 `.github/workflows/release.yml`을 트리거해 GHCR 이미지(`{버전}`, `{major}.{minor}`, `latest`)를 발행합니다.
- 릴리스 티켓은 Jira Subtask `웹 v{버전} 배포`입니다. 사용자가 티켓 키를 주지 않으면 요청합니다.

## 작업 흐름

### 1. 사전 확인

1. Jira에서 릴리스 티켓을 조회해 요약(`웹 v{버전} 배포`)에서 목표 버전을 확인합니다. 티켓이 없거나 버전이 불명확하면 진행하지 말고 사용자에게 확인합니다.
2. 직전 릴리스 PR 한 쌍(`gh pr list --state merged`에서 `release/*` 검색)을 열어 제목·본문 구조를 확인합니다. 이 스킬의 규칙과 실제 최근 PR이 다르면 최근 PR을 따르고 사용자에게 알립니다.
3. 릴리스 범위를 파악합니다: `git fetch origin && git log --oneline origin/main..origin/dev`. 이 커밋 목록이 릴리스 PR 본문의 변경 사항이 됩니다.
4. 범위에 포함된 각 기능 PR 본문을 읽고 "배포 시 확인 사항"(백엔드 선행 배포, 경로 변경, 운영 설정, 배포 후 검증 항목 등)을 수집합니다. 릴리스 PR 본문에서 가장 가치 있는 섹션이므로 대충 넘기지 않습니다.
5. 워크트리가 깨끗한지 확인합니다(`git status --short`). 더럽다면 정리하지 말고 사용자에게 확인합니다.

### 2. 브랜치·버전 커밋

1. `git checkout -b release/v{버전} origin/dev`
2. `package.json`의 `version`을 올립니다. 다른 파일에 이전 버전이 하드코딩돼 있는지 grep으로 확인합니다(현재는 `package.json` 한 곳뿐).
3. 검증을 실행합니다: `pnpm typecheck && pnpm lint && pnpm test`, 이어서 `pnpm test:e2e`. 릴리스는 커밋 직전이므로 E2E를 반드시 포함합니다.
4. 커밋 후 `git push -u origin HEAD`.

### 3. PR 2건 생성

두 PR 모두 이전 릴리스 PR의 본문 구조를 그대로 따릅니다. 작성에는 `technical-writing` 스킬(하네스)을 참고합니다.

**릴리스 PR (→ main)** 본문 구성:

- 요약: 이번 릴리스에 담긴 변경을 한 문단으로.
- 관련 이슈: 릴리스 티켓.
- 변경 사항: `[KNK-###] {Tag}: 제목 (#PR번호)` 목록 + 버전 변경 커밋.
- 화면: 각 기능 PR에서 검수 완료됐음을 명시(이 PR 자체는 버전 변경만).
- 검증: 실제로 실행한 것만 체크. 테스트 개수를 명시하고, 비주얼 회귀는 로컬에서 건너뛰므로 기능 PR CI 통과를 근거로 적습니다.
- 체크리스트: 제목 형식·릴리스 브랜치 규칙·Jira 범위·secret·프로덕션 환경 변수.
- **배포 시 확인 사항**: 1-4에서 수집한 항목. 백엔드 의존성·DB 마이그레이션이 없으면 "없다"고 명시합니다.
- 참고: 변경이 모두 dev에 머지된 상태라는 것, 머지 후 태그 푸시가 이미지를 발행한다는 것.
- 하단에 언급된 모든 `[KNK-###]` 키의 Jira 링크 정의를 붙입니다.

**dev 동기화 PR (→ dev)** 본문 구성: 개요(버전 커밋을 dev에 동기화), 포함 커밋, 참고(기능은 이미 dev에 있음) — 짧게 유지합니다.

둘 다 `gh pr create --draft`로 만듭니다.

### 4. CI 대기 → 머지

1. `gh pr checks`로 모든 체크가 pass가 될 때까지 기다립니다. Docker 빌드 잡은 15분 이상 걸릴 수 있으므로 백그라운드 폴링을 사용합니다.
2. CI가 실패하면 머지하지 말고 원인을 보고합니다.
3. **머지 전에 사용자 확인을 받습니다.** 사용자가 이미 "CI 통과하면 머지까지 해줘"처럼 명시적으로 위임한 경우에만 확인 없이 진행합니다.
4. 릴리스 PR을 먼저 머지합니다: `gh pr ready` → `gh pr merge --merge`.
5. dev 동기화 PR을 머지합니다: `gh pr merge --merge --delete-branch`. 이때 릴리스 브랜치가 삭제됩니다.
6. `git fetch origin --prune`으로 로컬 추적 브랜치까지 정리하고, 두 머지 커밋이 모두 버전 커밋을 부모로 갖는지 확인합니다.

### 5. 태그 → 릴리스 워크플로 → Jira

1. main 머지 커밋 SHA에 lightweight 태그를 붙여 푸시합니다:
   ```bash
   git tag v{버전} {main-머지-커밋-SHA}
   git push origin v{버전}
   ```
2. `gh run list --workflow=release.yml`로 태그가 트리거한 Release 워크플로를 찾아 성공까지 확인합니다. 성공해야 GHCR 이미지가 발행된 것입니다.
3. Jira 릴리스 티켓을 완료로 전환합니다(Atlassian MCP `transitionJiraIssue`, "작업 완료" 또는 "완료" 트랜지션).

### 6. 완료 보고

- 머지된 PR 2건(번호·머지 커밋 SHA), 태그와 대상 커밋, Release 워크플로 결과, Jira 전환 결과를 표로 보고합니다.
- 기능 PR에서 수집한 **배포 후 후속 작업**(운영 설정, 배포 후 검증 항목 등)을 다시 상기시킵니다. 코드 배포로 해결되지 않는 항목이 잊히기 쉽습니다.

## 금지 사항

- Jira 릴리스 티켓이 없거나 버전이 불명확한 상태로 시작하지 않습니다.
- E2E를 건너뛴 채 릴리스 커밋을 만들지 않습니다.
- CI가 전부 pass가 아닌 상태에서 머지하지 않습니다.
- squash·rebase 머지를 쓰지 않습니다. 항상 머지 커밋입니다.
- annotated 태그를 만들지 않습니다. 기존 관례는 lightweight입니다.
- 사용자의 명시적 위임 없이 머지·태그 푸시를 진행하지 않습니다. 되돌리기 어려운 단계입니다.
- `main`·`dev`에 직접 푸시하지 않습니다.

## 완료 기준

- `main`과 `dev` 모두에 버전 커밋이 반영됨 (각각 머지 커밋 경유)
- `release/v{버전}` 브랜치가 로컬·리모트에서 삭제됨
- `v{버전}` 태그가 main 머지 커밋을 가리킴
- Release 워크플로 success
- Jira 릴리스 티켓 완료
