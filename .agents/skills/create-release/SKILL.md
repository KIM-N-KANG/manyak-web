# 릴리스 진행 (manyak-web)

`dev`의 변경을 `release/v{버전}`으로 묶어 `main`과 `dev`에 머지하고, 버전 태그로 GHCR 릴리스 이미지를 발행합니다. 운영 호스팅 반영은 별도 확인 대상입니다.

## 실행 범위와 팀 규칙

- 브랜치 준비, PR 생성, 머지, 태그 푸시·이미지 발행 중 요청한 범위까지만 진행합니다. 브랜치 생성 요청을 전체 배포로 확대하지 않습니다.
- 대화에서 이미 승인받은 범위를 유지합니다. 머지·태그 푸시가 아직 승인되지 않았다면 준비와 검증을 마친 뒤 해당 단계 직전에만 확인합니다. 머지 승인만으로 태그 푸시까지 승인된 것으로 보지 않습니다.
- 브랜치는 최신 `origin/dev`에서 만든 `release/v{버전}`입니다. 버전 변경은 기본적으로 `package.json`의 `version` 한 줄이며, 커밋은 `[KNK-{티켓}] Chore: 패키지 버전 v{버전}로 변경`입니다.
- 같은 릴리스 브랜치에서 PR 2건을 만듭니다.
  - → `main`: `[KNK-{티켓}] Release: v{버전}`
  - → `dev`: `[KNK-{티켓}] Chore: v{버전} 버전 dev 동기화`
- 두 PR 모두 Draft로 생성하고 각각 CI 통과 후 Ready로 전환합니다. main을 먼저, dev를 다음으로 **머지 커밋**(`--merge`) 방식으로 머지합니다. squash·rebase를 사용하지 않습니다.
- `v{버전}`은 **정확한 main PR 머지 커밋**을 가리키는 lightweight 태그입니다. 현재 main 끝이나 로컬 HEAD를 대신 사용하지 않습니다.
- `main`·`dev`에 직접 푸시하거나 기존 브랜치·태그를 강제로 덮어쓰지 않습니다.

## 1. 사전 확인과 재개 지점

1. 티켓 키는 사용자가 명시한 값 → 현재 작업에서 대화로 확정한 값 → 현재 브랜치의 값 순으로 후보를 찾습니다. Jira에서 실제 릴리스 Subtask `웹 v{버전} 배포`인지 확인합니다. 기능 브랜치의 키를 릴리스 티켓으로 그대로 쓰지 않습니다. 키가 없거나 버전과 충돌하면 필요한 정보를 요청하고, 그동안 가능한 읽기 전용 조사는 진행합니다.
2. 현재 스킬, `.github/workflows/release.yml`, 하네스 `docs/product-specs/7-deployment.md`를 기준으로 진행합니다. 직전 릴리스 PR은 제목·본문 참고 자료입니다. 과거 예외가 현재 규칙을 덮어쓰게 하지 말고, 실제 충돌은 해당 단계 전에 해결합니다.
3. 원격 상태를 fetch한 뒤 로컬·원격 릴리스 브랜치, 해당 head의 main/dev PR(열림·머지·닫힘), 로컬·원격 태그와 관련 Release 실행을 조회합니다. **main PR 번호, dev PR 번호, 버전 커밋 SHA, 최종 릴리스 head SHA, 각 머지 SHA, 태그, 워크플로 실행 ID**를 확인되는 대로 기록합니다.
4. 신규 릴리스는 `origin/main..origin/dev`의 커밋과 기능 PR을 조사합니다. 재개 시에는 기존 릴리스 head를 기준으로 실제 포함된 변경을 조사하며, 뒤늦게 추가된 dev 커밋을 자동으로 끌어오지 않습니다. 기능 PR의 백엔드 선행 배포·운영 설정·배포 후 검증 항목을 수집합니다.
5. 신규 버전은 안정 버전 `X.Y.Z` 형식이고 기존 원격 릴리스 태그보다 높은지 확인합니다. 워크플로가 `latest`도 갱신하므로 이전 버전 재발행·프리릴리스는 이 절차로 그대로 진행하지 않습니다. 같은 버전의 재개는 기존 커밋·태그와 일치하는지 확인합니다.
6. 워크트리와 인덱스를 확인합니다. 작업 외 변경은 보존하고, 필요하면 별도 worktree에서 준비합니다. 기존 브랜치나 PR을 무조건 재생성하지 않습니다. 같은 head/base의 PR은 재사용하고, 닫혔지만 머지되지 않은 PR은 닫힌 이유를 확인한 뒤 처리합니다.

응답 오류나 중단 후에는 원격 상태를 먼저 다시 읽습니다. main만 머지됐다면 dev 동기화부터, 태그까지 푸시됐다면 해당 실행 확인부터 재개합니다. 후속 단계 실패를 이유로 이미 성공한 머지·태그를 취소하지 않습니다.

## 2. 브랜치·버전 커밋

1. 신규 릴리스일 때만 `git checkout --no-track -b release/v{버전} origin/dev`로 분기합니다. 기존 브랜치를 재개할 때는 원격과 로컬의 관계를 먼저 확인합니다.
2. `package.json`의 버전을 변경합니다. `rg`로 다른 버전 참조를 확인하되 과거 릴리스 기록이나 무관한 문자열을 일괄 치환하지 않습니다. 재개 시 이미 반영된 버전 커밋은 재사용합니다.
3. 릴리스 커밋 전에 `pnpm typecheck && pnpm lint && pnpm test`, 이어서 `pnpm test:e2e`를 통과시킵니다. 소요 시간을 이유로 필수 검사를 생략하지 않습니다. 동일 변경에 대한 유효한 검증 결과는 재사용하고, 후속 수정 시 영향받는 검사를 다시 실행합니다.
4. 릴리스에 필요한 변경만 스테이징하고 staged diff를 확인해 커밋합니다. PR 생성·게시가 요청 범위에 포함되면 대상 브랜치를 확인한 뒤 `git push -u origin HEAD`로 게시합니다.
5. 필요한 CI 수정이 추가되면 두 PR 본문과 검증 근거에 포함하고 최종 head SHA를 갱신합니다. 어느 한 PR이 이미 머지됐다면 릴리스 head를 임의로 바꾸지 말고, 두 브랜치에 같은 변경을 반영할 후속 처리 방안을 먼저 정합니다.

## 3. PR 2건 준비

하네스의 `.agents/skills/technical-writing/SKILL.md`를 참고해 현재 변경에 맞는 본문을 작성합니다. 여러 줄 본문은 파일에 작성하고 `--body-file`로 전달합니다. 신규 PR은 `--draft --head release/v{버전} --base main` 또는 `--base dev`로 대상을 명시합니다. 생성·재사용한 두 PR의 번호를 각각 기록하고, 이후 모든 PR 명령에 번호를 전달합니다.

**main PR**에는 다음을 담습니다.

- 요약, 릴리스 티켓, 포함된 기능 PR·커밋, 버전 변경 및 후속 수정.
- 화면·검증 근거: 직접 확인한 결과와 기능 PR의 확인 기록을 구분합니다. 기록이 없으면 검수 완료라고 쓰지 않습니다. 실행한 검사·결과와 확인 가능한 테스트 개수만 적습니다.
- 로컬 `pnpm test:e2e`는 비주얼 회귀를 검증하지 않습니다. 이번 최종 릴리스 head에 대한 Playwright CI 결과를 확인하고, 과거 기능 PR CI만으로 이번 릴리스 검증을 대신하지 않습니다.
- 배포 시 확인 사항: 수집한 백엔드 의존성·마이그레이션·환경 설정·배포 후 검증. 확인하지 못한 항목은 미확인으로 남깁니다.
- 태그 푸시로 GHCR 이미지가 발행된다는 설명과 관련 Jira 링크.

**dev PR**에는 버전 및 후속 수정 동기화 목적, 포함 커밋, main PR 링크와 검증 결과를 짧게 적습니다. 이미 dev에 있는 기능을 새 변경처럼 나열하지 않습니다.

## 4. 두 PR의 CI 확인과 머지

1. 두 PR의 head가 기록한 최종 릴리스 SHA인지 확인하고, `gh pr checks <main-PR번호>`와 `gh pr checks <dev-PR번호>`를 각각 확인합니다. base별 워크플로와 저장소 필수 체크를 확인하며, 미실행·대기·실패를 통과로 취급하지 않습니다. 장시간 대기는 짧은 조회나 백그라운드 실행으로 진행 상황을 확인합니다.
2. CI 실패는 원인을 확인해 요청 범위 안에서 수정하고 재검증합니다. 해결되지 않은 필수 검사 실패가 있으면 머지하지 않습니다. 승인 대기 중 head가 바뀌면 새 SHA 기준으로 다시 검증합니다.
3. 승인된 범위에서 아래 명령을 **각각의 PR 번호**로 실행합니다.
   ```bash
   gh pr ready <main-PR번호>
   gh pr merge <main-PR번호> --merge --match-head-commit <최종-릴리스-SHA>
   gh pr ready <dev-PR번호>
   gh pr merge <dev-PR번호> --merge --match-head-commit <최종-릴리스-SHA>
   ```
   이미 Ready이거나 머지된 PR은 해당 단계를 반복하지 않습니다. dev PR은 main 머지 뒤에도 자신의 CI·머지 가능 상태를 확인합니다.
4. 두 PR이 실제 `MERGED` 상태인지 조회해 각각의 머지 SHA를 기록하고 fetch합니다. 최종 릴리스 SHA가 두 머지 커밋의 부모에 포함되는지, 버전 커밋이 최종 릴리스 SHA의 조상인지 확인합니다. 버전 커밋 뒤에 수정이 있을 수 있으므로 버전 커밋 자체를 직접 부모로 요구하지 않습니다.
5. 둘 다 확인된 뒤 릴리스 브랜치를 정리합니다. 원격 브랜치와 로컬 브랜치는 각각 삭제하고 추적 ref는 `git fetch origin --prune`으로 정리합니다. 로컬 브랜치는 다른 브랜치로 이동 후 `git branch -d`를 사용하며, 추가 커밋·다른 worktree 사용 때문에 삭제할 수 없으면 보존하고 보고합니다. 강제 삭제하지 않습니다.

## 5. 태그와 GHCR 이미지 발행

1. 태그 푸시 승인 범위와 버전 일치를 확인합니다: 목표 버전, 릴리스 커밋 및 main 머지 커밋의 `package.json`, 태그 `v{버전}`이 일치해야 합니다. 기존 로컬·원격 태그가 있으면 종류와 대상 SHA를 비교합니다. 같은 lightweight 태그면 재사용하고, 다른 SHA나 annotated 태그면 덮어쓰지 않고 불일치를 해결합니다.
2. 태그가 없을 때 기록한 main PR 머지 SHA에 생성하고, 원격에 없을 때만 푸시합니다.
   ```bash
   git tag v{버전} <main-PR-머지-SHA>
   git push origin refs/tags/v{버전}
   ```
3. `gh run list --workflow release.yml --commit <main-PR-머지-SHA> --event push`로 후보를 찾고 **태그 이름·head SHA·워크플로·이벤트**가 모두 맞는 실행 ID를 확정합니다. 목록의 최신 실행을 무조건 선택하지 않습니다. 해당 ID의 성공 여부와 이미지 push 단계를 확인합니다.
4. 현재 워크플로는 GHCR에 `{버전}`, `{major}.{minor}`, `latest`를 발행합니다. 실행 실패·대기·미생성이면 발행 완료로 보고하지 않습니다. 이미 푸시한 태그를 이동하거나 삭제·재생성해 재실행하지 말고, 원인을 확인한 뒤 승인 범위 안에서 해당 실행을 재시도합니다.

## 6. Jira와 완료 보고

- GHCR 이미지 발행 성공과 운영 호스팅 반영을 구분합니다. 하네스 `docs/product-specs/7-deployment.md`의 웹 배포 규칙에 따라 실제 호스팅 반영·배포 후 확인은 별도 근거로 검증합니다. 이미지 발행만 확인하고 운영 배포 완료라고 보고하지 않습니다.
- 릴리스 티켓의 완료 조건을 확인하고 요청 범위 안에서 Jira 상태를 갱신합니다. 티켓이 운영 반영까지 요구한다면 해당 확인 전에는 완료로 전환하지 않습니다. 현재 상태가 이미 완료면 반복하지 않고, 전환이 필요하면 사용 가능한 transition을 조회해 목표 상태의 실제 ID로 실행한 뒤 상태를 다시 읽습니다.
- Jira 전환이 실패해도 성공한 릴리스를 되돌리지 않습니다. 남은 조치로 보고합니다.
- 요청 범위의 완료 상태를 보고합니다: 두 PR 번호·머지 SHA, 최종 릴리스 SHA, 태그 대상, Release 실행 링크·결과, GHCR 발행, 운영 확인, 브랜치 정리, Jira 상태. 아직 요청하지 않았거나 확인하지 못한 단계는 완료로 표시하지 않습니다. 배포 후 후속 작업도 함께 남깁니다.
